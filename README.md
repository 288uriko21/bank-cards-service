# 🚀 Система управления банковскими картами

Backend‑приложение на Java / Spring Boot для управления банковскими картами: создание и управление картами, просмотр, переводы и базовая безопасность.

---

## ✅ Текущий функционал

### Пользователи и роли

- Пользователи и роли (`ADMIN`, `USER`) хранятся в таблице `users` базы данных.
- Аутентификация идёт через Spring Security и кастомный `UserDetailsService`, который загружает пользователей из БД.
- Роль пользователя берётся из поля `role` (`ADMIN` / `USER`) в `UserEntity` и используется для ограничения доступа.

### Карты

Сущность `CardEntity` с полями:

- номер карты (строка, хранится в БД, в API возвращается в маскированном виде `**** **** **** 1234`);
- владелец (`UserEntity`);
- срок действия;
- статус (`ACTIVE`, `BLOCKED`, `EXPIRED`, `DELETED`);
- баланс.

Эндпоинты:

- `GET /api/cards` — все карты, только для `ADMIN`.
- `GET /api/cards/my` — карты текущего аутентифицированного пользователя.
- `POST /api/cards` — создание карты:  
  - `ADMIN` может создать карту любому пользователю по `userId`;  
  - `USER` может создать карту только себе (даже если в запросе передан другой `userId`).
- `PATCH /api/cards/{id}/block` — блокировка карты (только `ADMIN`).
- `PATCH /api/cards/{id}/activate` — активация карты (только `ADMIN`).
- `DELETE /api/cards/{id}` — мягкое удаление (статус `DELETED`, карта остаётся в истории).
- `POST /api/cards/{id}/block-request` — запрос блокировки своей карты (для владельца).

### Переводы и транзакции

Сущность `TransactionEntity`:

- `fromCard`, `toCard`, `amount`;
- `createdAt`;
- `status` (`SUCCESS`, `FAILED` и т.п.);
- `message` (причина ошибки);
- `type` (`INTERNAL`, `EXTERNAL`) — тип операции.

#### Виды переводов

**Внутренний перевод между своими картами (`INTERNAL`):**

- `POST /api/transfers` — перевод между двумя картами текущего пользователя.
- Проверяется:
  - что обе карты принадлежат пользователю;
  - статус карт (`ACTIVE`);
  - достаточность средств.
- Создаётся транзакция со статусом `SUCCESS` и типом `INTERNAL`, обновляются балансы.

**Внешний перевод (`EXTERNAL`):**

- `POST /api/transfers/external` — перевод с карты текущего пользователя на любую другую карту.

Для `USER`:

- списывать можно только со своих карт;
- действует суточный лимит по сумме внешних переводов;
- при превышении лимита или недостатке средств создаётся транзакция со статусом `FAILED` и причиной.

Для `ADMIN`:

- можно переводить между любыми картами;
- лимит не применяется.

**История операций:**

- `GET /api/transfers/my` — история переводов, где текущий пользователь был отправителем.
- Возвращается список DTO `TransactionHistoryItem` (`id`, `fromCardId`, `toCardId`, `amount`, `status`, `message`, `createdAt`).

### Обработка ошибок

- Глобальный обработчик исключений (`GlobalExceptionHandler`) возвращает единый формат `ApiError`:
  - `timestamp`, `status`, `error`, `message`, `path`.
- Отдельное бизнес‑исключение (`BusinessException`) для бизнес‑ошибок (лимит, недостаток средств и т.д.):
  - при таких ошибках:
    - создаётся `TransactionEntity` со статусом `FAILED` и нужным `message`;
    - транзакция **не** откатывается;
    - наружу уходит HTTP 400 с `ApiError`.

### Безопасность

- Spring Security c:
  - загрузкой пользователей из БД через `JpaUserDetailsService`;
  - ролевым доступом к эндпоинтам через `SecurityFilterChain`:
    - `GET /api/cards` и операции изменения статуса/удаления — только для `ADMIN`;
    - остальные операции с картами и переводами — для любого аутентифицированного пользователя.
- Номера карт маскируются в DTO.

### Инфраструктура

- БД: PostgreSQL в Docker‑контейнере.
- Данные хранятся в Docker‑томе, поэтому сохраняются между перезапусками контейнера.
- Работа с БД через Spring Data JPA, таблицы соответствуют сущностям `UserEntity`, `CardEntity`, `TransactionEntity`.
- Настроено логическое мягкое удаление карт через статус `DELETED`.

Чтобы довести проект до состояния, максимально близкого к ТЗ и улучшить его как пет‑проект, дальше план такой.

- Добавить `LoginRequest` / `LoginResponse`, `JwtUtil`, `AuthController` (`POST /api/auth/login`).
- Генерировать JWT на основе пользователя из БД, хранить роли в клеймах.
- Добавить фильтр, который извлекает и валидирует `Bearer`‑токен и наполняет `SecurityContext`.
- Обновить `SecurityConfig`, отключив `httpBasic` / `formLogin`.

### Поиск и пагинация для `/api/cards/my`

- Параметры `page`, `size`, возможно фильтры по статусу / последним цифрам.
- Возврат `Page<CardResponseDto>` или собственного объекта с `content` + `total`.

### История операций по карте

- `GET /api/cards/{id}/transactions` с проверкой владельца / `ADMIN`.
- Пагинация, сортировка по `createdAt`.

### Документация и тесты
